## 实现

- `ps_app/src/wcis_camera_owner.cpp`：显式启用 `WCIS_WEB_PREVIEW_JPEG_FPS=15` 时，CPU 线程从已有不可变最新帧槽取 RGB565，转为 JPEG（质量 75）。只有最新帧，不排队；不调用 SDK、不改模型帧、不另开 VPU。通过 tmpfs 原子替换 `preview-jpeg.frame` 发布源帧号、boot/PID、捕获时间及图片。退出时 join；JPEG 出错只停止此预览输出，失效图片由读端拒绝，不解除硬件隔离。
- `lan_stream/vpu_live_server.py`：新增网页专用 `read_preview()`，保留 boot/session/PID、源尺寸、进程和新鲜度检查；一秒以上旧图片拒绝显示。原 `read()` 继续返回 H.264，供录像与原媒体接口使用。
- `npu_photo/serve_photos.py`：网页状态、逐帧流和快照使用 `read_preview()`。现有页面已经支持逐帧 JPEG，因此没有重做 UI。检测图仍绑定自己的检测帧。
- H.264 编码、1 秒分片、原播放器及独立录像逻辑恢复为 r2/原录像版本。前面的短分片和追帧试验未混入最终方案，源码与测试另保存在 `outputs/preview-low-latency-20261102/experiments/`。

复用的是逐帧传输/显示方式；当前预览 JPEG 由 CPU 编码，不应写成复用了旧 VPU JPEG 编码路径。代价是额外 CPU 和网页带宽，预览帧率为 15，而采集/录像仍约 30 fps。

## 本次实测

约 132 秒录制并周期调用识别，采样 63 次、首末跨度 131.04 秒：

| 项目 | 结果与范围 |
|---|---|
| 网页 JPEG 源帧率 | 约 14.97 fps；正式浏览器显示约 15 fps，并实际呈现画面 |
| 采集帧率 | 约 29.56 fps，与预览源计数分别统计 |
| 已发布 JPEG 距捕获请求的年龄 | p50 109.8 ms，p95 145.2 ms，最大 178.1 ms；不是摄像头到屏幕的光学总延迟 |
| 固定输入模型输出 | 同一 PNG 两次重放，YuNet 和 MobileFaceNet 原始输出散列及检测框与 r2 基线一致 |
| 现场请求 | 10 次均为无人脸；核对 boot/PID/源帧号、原始输入和结果 JPEG 散列归属。不能称真人 PAD 或多脸验收 |
| 录制 | 新增三段 MP4，1800、1770、360 帧，共 3930 帧；正常收尾恢复 off/idle，队列丢帧 0 |
| 资源 | 六个视觉进程本窗口平均约 1.24 核，末次 RSS 合计约 251.4 MiB；包含网页、识别和录像，缺同负载 r2 对照，不能宣称省 CPU 或给出精确增幅 |
