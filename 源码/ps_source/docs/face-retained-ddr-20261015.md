## 实际数据路径

PS 解码并整理一次 BGRX → SDK 分配并上传一次 PL DDR 原帧 → PL 缩放 →
PS 读回及张量转换 → NPU 检测 → PS 求五点对齐参数 → PL 对齐引用同一 DDR 原帧 →
PS 读回及张量转换 → NPU 特征提取 → PS 使用缓存的登记特征比对。

此前只复用PS临时像素文件，两次PL程序仍分别上传原图。现在第二次对齐不再上传原图。
输出读回、PS像素/浮点转换和NPU输入传输仍存在，不能称整条链路零拷贝。
后续摄像头可以复用帧描述和保留/释放规则，但尚未实现摄像头采集入口、连续缓冲或帧调度。

## SDK 所有权与地址隔离

不能直接保留一个已关闭设备的SDK内存对象，也不能让NPU重新分配时覆盖原帧。
实现采用CPU侧帧租约，完整请求持有原有 `npu.lock`，设备按阶段顺序交接：

1. 由SDK正常分配地址，不对猜测地址探测；在已验证FAC1 128 MiB地址窗口内，
   每帧含头尾保护、像素源和最大输出暂存，总量继续限制为64 MiB。
2. SDK内存对象在 `Device::Close` 前释放，不跨关闭保留对象。DDR帧的逻辑占用权
   由当前请求及帧工作进程保持；未完成的帧不允许被其他项目请求接管。
3. 检测、对齐、特征模型每次重新打开设备后，均先通过SDK定址分配接口保留同一区间。
   NPU在建立会话前完成保留；运行中检查分配器区间，读回帧头尾保护信息。
4. 每个阶段的张量、会话和内存对象退出作用域后关闭设备，再回复。
   身份使用 `boot_id + frame_id + frame_token`，不把局部frame_id当作全局唯一编号。
5. 请求结束释放CPU侧租约并退出帧进程；EOF等待在途命令结束，不强杀SDK/DMA所有者。
   异常沿用本次启动隔离和禁止自动重试规则，不回退CPU预处理。

共享设备安全仍要求所有访问遵守项目的完整请求独占约定；不支持其他程序绕过锁同时操作设备。
动态保留只覆盖本次SDK分配区间，没有扩大到整块2GB PL DDR，未做全DDR容量验收。
保护字不等同于每次检查全部像素：完整逐字节读回用于验证路径，生产路径不下载整帧做校验。

## 验证结果

- 先在已确认的现役BOOT上，只访问SDK分配的4 MiB区间：关闭/重新打开设备后数据一致，
  定址保留后其他正常分配跳过该区间。该小试验不是完整容量/吞吐验收。
- 11张单人照片及无脸、多脸，共13场景：PL输出像素SHA、NPU原始输出SHA、特征、框和
  身份状态与旧版本一致。保持原阈值及识别算法；不代表更广泛准确率。
- 对每次检测及存在时的特征模型运行后，完整读回原帧并与PS固定副本逐字节比较，
  共24次通过，源帧大小覆盖约0.9～11.2 MB。完整回读只在验证中启用。
- 12次交替照片请求、调用方原数组被覆盖、错误帧号拒绝及后续正常请求通过。
- 隔离HTTP服务两次真实NPU登记、追加、坏图拒绝、原图/MIME、删除、异常提交恢复、
  错误/丢失挂载检查通过。验证人员及临时目录清理，正式人员JSON及原图SHA保持不变。
- 正式切换后3次同图识别通过，帧token互异、缩放和对齐引用相同租约、原帧上传计数为1；
  NPU确认帧保留和设备关闭。空闲时无PL帧工作进程、无NPU设备文件句柄、无交换区遗留。
