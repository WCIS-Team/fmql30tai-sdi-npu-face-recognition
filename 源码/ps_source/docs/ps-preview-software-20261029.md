经用户同意，已部署 `camera-psopt-20261029` 与 `recording-psopt-20261029`。首次切换发生 VPU 出队错误，已保存失败记录、恢复原配置并正常重启；新启动上的一次受控切换通过。以最终 `promotion-clean-boot.json` 为准，不以隔离测试替代正式结果。

| 同次启动、各约 10 秒空闲窗口 | 原版 | 优化版 |
|---|---:|---:|
| 采集/编码进程 CPU 核数 | 0.4902 | 0.3117 |
| 录像服务 CPU 核数，mode=off | 0.1478 | 0.0779 |
| 两进程合计 CPU 核数 | 0.6380 | 0.3896 |
| 板端发布速率 | 29.75 fps | 29.77 fps |

合计减少约 0.2484 核，即两进程合计约减少 38.9%；按四核整机折算约 6.2 个百分点。以上来自进程 CPU 时间差，不是实测整机总负载降幅或 VPU 利用率。帧率是板端发布速率，不是浏览器显示帧率。

## 实现过程与契约

1. `ps_app/src/wcis_camera_owner.cpp` 在创建工作线程前调用 C++ `cv::setNumThreads(2)`，支持 `WCIS_OPENCV_THREADS=1..4` 显式对照。Python 的同名设置不能调整此 C++ 子进程。模型、源格式、预处理计算和输出检查保持原有契约。
2. 同文件 `status()` 对相同状态每秒最多写一次；状态变化立即写，写入失败仍报错。`latest.frame` 继续逐帧发布。已核对 `Frames.read()` 从图像包读取 `captured_at` 判断新鲜度，并验证启动、来源和进程，不依赖状态文件里的旧帧号。
3. `lan_stream/vpu_live_server.py` 新增供录像使用的 `read_if_changed()`。以控制文件及图像包的 inode、纳秒修改时间和大小识别更新；同帧避免重复读取/解析，未变时每 250 ms 完整检查健康。错误回到原校验路径。token 在读取前采样，并发替换会促使下一轮重新读取；原 `read()` 接口保留。
4. `npu_photo/recording_service.py` 保持每 10 ms 检查新帧，仅在读取方返回帧或健康状态时调用 `ingest()`。off 模式原本也保留预录缓存，直接改为 500 ms 抽帧会改变行为，因此没有采用该建议。
