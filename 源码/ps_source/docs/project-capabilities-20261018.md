## 当前结论

项目已经具备可用的文件/模拟视频输入人脸ModelBackend，以及独立运行的1080p PL JPEG编码与eMMC保存原型。
照片服务可以逐脸识别最多4人、显示姓名或未知，并管理持久化人员库。
这两路功能已存在于同一整板固件，但测试软件仍强制互斥；真实SDI连续输入、识别与录像并行、
人脸事件录像和长期性能尚未完成，不能称为已经完成的实时摄像头识别录像系统。

项目当前仍以ModelBackend为范围。下文设备/缓冲工作属于后端接入前提；
事件状态机与录像调度仅描述接口和行为，不在本轮扩写OrchestrationLayer或WebFrontend。

## 实测性能应如何理解

| 测量对象 | 已有结果 | 正确口径 |
|---|---:|---|
| 1080p拼图2/3/4人识别 | 912.25 / 1056.75 / 1197.66 ms | 已预热单次板端处理；四人约0.83轮/秒为倒数折算，不是持续帧率 |
| 四人正式HTTP结果 | 处理1214.31 ms，请求内部计时1400.82 ms | 两种范围不同；均不是电脑到浏览器完整往返 |
| 四人视频2帧 | 板端1007.29 / 994.22 ms，本机往返2063 / 2000 ms | 只有两帧，不能推断长期性能，也不能据此保证视频总是更快 |
| 单人768×432视频 | 处理约561～566 ms，往返约649～656 ms | 旧短样本；不等于1080p四人性能，不含初始化与录像并发 |
| 1080p JPEG板内重新编码 | RGB565 23.895 FPS，BGRX 23.873 FPS | 原帧已经驻留DDR；不含新帧采集/输入和完整持久化 |
| JPEG重新编码、读回、eMMC写入及末尾fsync | 17.456 / 19.354 FPS | 每格式300次短测，真实落盘口径；仍未证明长期20 FPS |
| 本机新原帧至JPEG落盘 | 1.736 / 0.895 FPS | 含SSH原帧输入，受100 Mbps网络等影响，不能用作SDI吞吐结论 |

JPEG编码核约23.9 FPS，相对20 FPS目标的余量仅约19.5%，而且尚未与识别争用DDR。
“四人2轮/秒”意味着长期每秒完成8份身份结果；四人每轮500 ms的目标与当前约1.20秒仍有明显差距。
若后续重叠流水，应分别验收完成率和从采集到结果的延迟，不能只取某一阶段耗时的倒数。

## 优化排序与依据

### 1. 先核清并发契约，再做识别与录像共存

进一步实施：[实际NPU/JPEG重叠](npu-jpeg-parallel-20261018.md)在现役位流上通过30组成对板测，
观察真实卷积完成时JPEG仍忙，结果与串行一致。新FAC1/JPG1公平仲裁已通过仿真，未部署。

后续实施：[同帧识别与PL JPEG分时共存](face-jpeg-coexist-20261018.md)已经过学校交叉编译和板测，
18个完整帧、96次NPU调用、36张JPEG通过输入/输出与原帧保护核对；原图每帧只上传一次。
这是独立ModelBackend有界测试，正式HTTP与旧JPEG启动器尚未切换；下面保留最初问题及验收依据。

事实：`scripts/launch_jpeg_stream.py`会暂停照片服务；JPEG与识别接收器整段持有同一把`npu.lock`。
因此现状是软件禁止两路同时使用设备，不只是缺一次并发测试。
`rtl/wcis_recording_customop.v`已同时实例化FAC1与JPEG，但共用DDR接口，JPEG固定优先，且仅一笔native读事务在途。
它保持背压时的请求归属，却没有保证人脸请求最大等待时间的公平仲裁。

建议先基于厂商SDK/CustomOp已有接口验证：设备开关的影响范围、DDR分配器是否共享、NPU会话能否覆盖另一客户端内存、
读回完成前谁持有原帧与输出。形成有界缓冲描述符，至少包含帧号、时间戳、格式、stride、有效范围和释放条件。
保持单一资源所有者，在SDK支持范围内验证安全重叠或短时分时；不能直接删除全局锁或增加多个独立SDK客户端。
必要时再更改仲裁，并为双方定义最大等待与背压行为。

验收：同一启动中交错运行真实检测/特征与JPEG，结果及源帧校验一致，缓冲无覆盖、无泄漏、无死锁，错误后可控释放。
先做有界并发试验，再设计长期运行；不以整板同时存在两套核替代这一步。

### 2. 优先减少输入准备、会话与数据交换成本

本次重读四人HTTP原始结果`http-four-result.json`，分段为：

| 阶段 | 同一样本耗时 |
|---|---:|
| 输入准备`prepare_ms` | 468.52 ms |
| 检测调用 | 146.93 ms |
| 4次对齐合计 | 约109.76 ms |
| 4次特征调用合计 | 约425.06 ms |
| 4次身份库比对合计 | 约4.51 ms |

输入准备内包含打包、临时内存文件、SDK/PL处理、结果读回和张量准备等，不能把469 ms统称为PL计算。
首个PL job的`pl_and_readback_ms`约53.98 ms；该项包含读回，也不是纯核心时间。
第一张脸的特征调用内，会话建立61.51 ms，`forward_and_wait`21.27 ms，设备打开13.62 ms。
这里未启用SDK硬件计时，21.27 ms也不能当作纯NPU核时间。

判断：当前有充分理由先查数据搬运、临时交换和SDK生命周期；尚无理由先做人员库比对的PL加速或直接更换模型。
即使把当前输入准备全部消除，该HTTP样本仍约746 ms，单靠省掉PS原帧准备不能保证四人500 ms。

建议按成本从低到高试验：视频入口关闭非必要诊断图/重复中间产物；复用有界缓冲；减少格式/float张量往返；
核实SDK支持后评估同一帧多脸特征调用复用设备/会话；再根据分段瓶颈评估PL连续读取、行缓存及输入布局。
不要假定已编译模型支持batch=4，也不要把SDK进程多开当成NPU可并行。

验收：相同输入、相同库、已预热条件下做配对对照，记录p50/p95和逐段时间；同时复核原始模型输出、框/身份及DDR保护。
降低校验或关闭证据保存须区分功能验证模式与正常运行模式，不能只靠少做正确性检查制造提速。

### 3. 打通JPEG编码与写盘的重叠，保留持久化口径

300帧短测的末尾fsync等待约2.735～4.409秒，表明需关注集中写回等待。
建议有界压缩队列、编码/读回/写盘重叠、按段保存及明确的同步策略；队列满时明确丢帧或降采样行为。
删除fsync会改变断电可恢复范围，不能据此宣称落盘提速；fsync语义见[Linux手册](https://man7.org/linux/man-pages/man2/fsync.2.html)。
应测队列峰值、写盘尾延迟、完整JPEG数及录像时间戳；原帧重复编码测试只能验编码/保存支路，不能验真实采集。

### 4. 事件录像先定接口，再接业务控制

沿用2026-10-17最新选择：保留PL JPEG路线；本轮不切换VPU或H.264。
检测到有效人脸即可触发，未知身份也触发，无需等待身份比对；当前尚无独立检测触发路径的持续性能证据。
候选行为是检测后开始保存、无人脸后延迟结束、有界预录缓存、分段和独立录像配额；这些均未上线。
有预录要求就必须在待机继续编码并保留近期JPEG；停编码省负载会失去触发前画面，需要明确取舍。

按既有样本20 FPS估算，MJPEG约11.61～12.45 GB/录像小时。
事件触发只减少无人时的保存占比；一直有人时仍按连续录像消耗空间。
历史约30.63 GB可用量不是本轮重新查询的剩余量，不能直接当成当前剩余容量。
轮转只能作用于录像目录，不能删除人员库；预录、收尾、检测延迟及磁盘满都需明确行为。

### 5. 验证真实场景准确率与长期性能，最后接真实采集验收

四人测试主要为公开照片拼图，证明遍历、结果绑定和数量上限；不能证明真实多人、遮挡、运动模糊、侧脸和小脸准确率。
建议用独立的真实场景登记/查询数据评估误认、拒识、漏检及相似度分布，保留小脸/模糊等分组结果；不要仅为提高通过率降低阈值。
尚无活体检测，不能以照片识别成功支持门禁级抗照片攻击的结论。

摄像头仍由用户线下调试；后台先沿用当前文件/SSH测试源，完成ModelBackend与并发前提，避免把模拟网络速度当作待优化的最终链路。
后续真实采集验收需覆盖跨时钟、持续DMA、帧所有权、格式与stride、满队列丢帧、录像与识别争用。
建议长期试验同时报告录像实际完成FPS/丢帧、逐人身份更新间隔、p95延迟、队列峰值、内存及磁盘余量。
时长、容许丢帧和断电丢失窗口应先定指标；20 FPS和四人2轮/秒仍是待验收目标。
