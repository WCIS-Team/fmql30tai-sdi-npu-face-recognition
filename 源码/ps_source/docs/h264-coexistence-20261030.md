## 带模型负载的对照

先在独立任务中让 VPU 编码并排空 30 张合成灰图，再打开 SDK；灰图不计为真实预览。正常保留模型 reset(1)，所有模型仍由单 owner 调用。

| 实现 | 结果 |
| --- | --- |
| VPU 先初始化，原六缓冲 | 空闲约 27 fps；模型负载下停帧/采集超时 |
| 额外预热全部模型 | 未解决 |
| 去掉码率控制，保留原 GOP/profile/QP | 空闲约 27.4 fps；识别时采集超时 |
| 编码控制改到分配缓冲之前，重新读取格式，六缓冲 | 编译通过；识别时仍采集超时 |
| 上一版本改四缓冲，连续八次单脸重放（含两次预热） | 一次短窗通过，混合窗口仅 2.62 秒、约 22.9 fps，不能称稳定 |
| 同一四缓冲版本重新启动，计划 122 次重放 | 两次重放后再次采集超时，推翻稳定修复判断 |
| 四缓冲，每条识别命令暂停并排空摄像头，等待输入线程空闲，保留 VPU 会话和在途编码 | 122 次重放完成，模型输出内部一致，正常关闭并恢复原服务；性能如下 |

最后一项没有把 VPU 彻底停流，也没有等待所有编码输出排空后才执行每个命令；摄像头请求在命令执行期间暂停，结束后恢复。原厂要求的模型完成复位保留。它是应用层受控分时方案，不能称硬件已经完全并行或唯一根因已定位。

最后一次测试：两次模型预热、120 次连续单脸检测/身份/双 PAD 重放，持续识别窗口约 9.90 fps，单次完整请求中位 663.86 ms，owner CPU 约 0.267 核；空闲十秒窗口计数约 27.20 fps、0.312 核。对比原四缓冲短窗约 375.59 ms，请求变慢。CPU 只包含 native owner；没有网页、录像、浏览器和整机开销。状态计数每秒更新，短窗 fps 有量化误差。保存单脸重放不是现场真人/攻击测试，PAD 未校准。

## 案例与编码封装审查补充

本次为只读源码/案例检查，没有新增硬件编码试跑。唯一物理根因仍未知。`Annex-B start code missing` 只是应用解析断言，失败原始输出包没有完整留存，不能单凭该字符串断言固件生成了坏码流；还须记录原包、bytesused、offset、flags、sequence 和时间戳，区分编码失败、取错位置及包边界假设。已有内核 MMU ABORT/watchdog 则确实是独立的底层错误证据，二者不能混成同一原因。

发现的代码问题和契约缺口：

1. `ps_app/vendor/include/pipeline/vpu/vpu.h:577/597` 把 `VIDIOC_REQBUFS` 失败与 `input_print_`/`output_print_` 相与后才抛错；两个日志标志默认 false。分配错误检查不应依赖日志开关。封装还按请求数量建立映射，没有按返回的实际数量驱动后续流程。这些是源码可直接确认的问题，但本次没有相应失败 ioctl 收据，不能称它们就是停帧根因。
2. 当前 `stop_h264()` 以应用层 `h264_pending` 为空作为排空条件，随后停止取流线程、STREAMOFF。未实现标准 encoder STOP/LAST 及独立回收原始输入队列的完整 drain。内核文档说明输入缓冲可能继续被用作参考帧，不能由收到等量 VCL 输出就推断设备所有缓冲已归还。需要区分完整无损 drain 和允许丢弃在途数据的 abort/STREAMOFF，不应宣称少了 EOS 就必然导致这次故障。
3. 通用 V4L2 允许一个输入产生多个输出缓冲，支持时间戳匹配；当前按一个含 VCL 的包弹出一个待编码帧的假设需要针对实际驱动证明。没有直接证明它在本次被违反。
