## 已验证的原型

改用板上现有 FFmpeg 4.2.7 的 `h264_v4l2m2m`，仍由硬件 VPU 编码。FFmpeg 的默认输出缓冲数是 16，本驱动实验固定输入 6、输出 4；不把默认配置当作本板兼容配置。先产生有界合成灰图让 VPU 真正输出，再打开 SDK/真实摄像头，灰图不计为摄像头结果。没有修改 RTL、BOOT、驱动、共享 SDK 或模型复位契约。

| 实验 | 结果与边界 |
| --- | --- |
| 保存的 1080p UYVY，四次独立开关 FFmpeg | 各 120 帧完整解码；无模型/实时采集；约 1.75 CPU 秒/4.43 秒，并非零 CPU |
| SDK/模型先初始化，再编码 | MMU ABORT，正常保留隔离证据后重启；不能断言唯一物理根因 |
| VPU 真正输出后打开 SDK，保存输入和模型重放 | 900 帧/30 秒全帧解码，24 次单脸/身份/双 PAD；没有实时摄像头 |
| 真实完整 1080p + FFmpeg + 模型 | 3 次现场无人脸请求和 8 次保存单脸重放后采集 DMA 超时；1080p 直送未验收 |
| 540p NV12 输给 FFmpeg 再转换 UYVY | 可并行但约 18.37 fps，空闲 native+FFmpeg 约 1.19 核；不接受为低负载优化 |
| 540p 在 native 用 NEON 将 I420 交织成 UYVY，FFmpeg 不做颜色转换 | 120 次重放全部逐项一致；1845 张真实输入约 29.55 fps；无需逐条暂停采集 |
| 直接 HLS/fMP4 封装 | 有缺失 PPS/解码失败，未接受 |
| 硬件 Annex-B 后交给第二 FFmpeg 解析 SPS/PPS，`-c:v copy` 封装 HLS/fMP4 | 120 次逐项一致，4579 张真实输入约 29.61 fps；4639 帧（含 60 灰图）全部解码；后台浏览器连续播放，960×540、无媒体错误 |

最后一个原型同时从相同 H.264 码流复制封装一段独立 eMMC MP4，12.034 秒、361 帧，逐帧解码通过；HTTP 浏览器实时播放时间从 56.3991 秒推进到 132.9816 秒。第二 FFmpeg 只复制封装，没有第二次视频编码。原型测试为 `hls-parser-result.json`、`browser-playback.json`；不是原网站集成验收。

原型空闲 native/编码/封装分别约 0.462/0.092/0.006 核，模型连续负载约 0.645/0.085/0.006 核；模型完整请求中位 377.09 ms。只统计这些进程，排除浏览器、网页、录像和测试编排，不等于整机占用。VPU 码率设置为目标值，标准 GOP/帧率控制被驱动拒绝；实码流检查为 Main、无 B 帧，固定 900 帧含 30 I/870 P，不能承诺严格码率控制。现场近黑静态画面，18,011 字节的短 MP4 不能外推一般压缩比或正常场景画质。

1080p UYVY 每帧 4,147,200 字节；30 fps 时单路原始有效载荷为 124,416,000 字节/秒，即 124.416 MB/s（十进制），是 540p 同为16 bit/像素输入的四倍。这仅是一次单向有效载荷，不是已测总内存带宽；实时 DMA、CPU 多次复制、编码器读写及其他访问会额外产生流量。H264 输出码率小，不能抵消编码之前的原始图像搬运。

已有对照仍是：保存的 1080p + VPU + NPU 通过，实时 1080p + VPU 单独曾通过，实时 1080p 加 NPU 失败。既可能是吞吐/突发服务延迟问题，也可能是缓冲所有权、控制时序、共享地址或驱动契约错误。MMU ABORT/DMA timeout 本身不是“满载”的诊断码。

下一组有区分力的测试应保持 1080p/像素格式/识别负载不变，实际限制 DMA 采集与 VPU 输入到 5、10、15、30 fps，同步记录逐核 CPU/线程、缓冲队列、DMA 完成延迟和可用的带宽计数器。只降低编码器输出帧率而让采集仍全速运行，不能检验采集带宽压力。低速仍失败更支持同步/契约问题，但不能完全排除单帧突发瓶颈；随输入速率提高而重复失效支持负载/反压方向，也不自动证明芯片算力上限。

实际分档进度见 [1080p 采集限速测试](h264-1080-load-sweep-20261030.md)：5、10 fps 各完成 60 次固定人脸请求并全部编码/解码通过；15 fps 完成 24 次后出现采集 Error 标志，约 19ms 返回，并非两秒等待超时。后台负载混杂尚未排除，30 fps 未测试，不能给出性能上限。用户要求先等正在运行的语音任务结束，再继续剩余测试；当前正式 540p H.264 服务已恢复。
