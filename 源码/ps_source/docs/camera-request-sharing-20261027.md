# 摄像头请求合并与防伪耗时显示（2026-10-27）

## 问题和证据

用户反馈页面持续显示“后台忙”，且检测耗时增加。正式日志显示 192.168.1.107 与 192.168.1.109 两个客户端同时自动 POST 摄像头识别接口，成功的 200 与冲突的 409 交替出现；不是后端完全停止。前端固定 250 ms 重试，又把每次 409 覆盖到防伪状态，导致成功结果很快被忙提示盖住。

初步降低重试频率后，第三个临时验证页面仍出现长时间等待；因此仅改提示不足以解决多客户端重复推理。本次最终加入后端合并，同时保留界面退避和证据过期保护。

## 最终实现

- `npu_photo/camera_requests.py`：同时到达的摄像头请求共享一份在途检测的结果和对应 JPEG。最多 8 个等待者，跟随请求等待上限 15 秒；等待超时不取消正在访问硬件的请求。完成后不缓存给下一轮请求，因此下一轮仍获取新帧。响应单独复制，更新防伪证据的交付帧龄，过期标记为 stale。
- `npu_photo/serve_photos.py`：只对零长度请求体的 `/api/recognize-camera` 接入合并。照片上传、人员库修改与硬件互斥保留；其占用仍可返回 409，等待者数量超限返回 429。健康接口公开 `camera_request_policy=share_inflight_only`。
- `npu_photo/camera_owner_runtime.py`：增加 `pipeline_timing_ms.identity` 与 `pad`，分别覆盖采帧到身份处理结束，以及之后的防伪评估。总耗时仍覆盖完整链路，不通过省略防伪或改标签隐藏耗时。
- `npu_photo/camera_panel.js`：正常检测完成后按耗时留出间隔；遇占用指数退避并加入随机错峰。短暂占用不覆盖仍有效的对应帧证据，但不延长其有效期。未成功启动的手动检测明确说明本次未开始。显示总耗时及“人脸 / 防伪”分项。

## 验证

5 项 Python 并发测试通过：多个读者仅执行一次操作、响应独立、下一轮执行新操作、等待超时不取消硬件、等待数量限制、异常释放与过期标记（部分检查合并在同一测试内）。4 组 Node 回归通过：竞争退避/有效结果保留/过期/恢复/手动请求、PAD 状态映射、预览独立与暂停单次检测、检测框对应。Python 和 JavaScript 语法检查通过。

正式板端 3 轮每轮 4 个并发请求，共 12 个全部成功；每轮同一 frame_id，至少 3 个跟随共享，三轮 frame_id 均不同。该次现场无人脸：完整处理分别约 421.75、295.27、310.06 ms；HTTP 收到结果约 363～529 ms。防伪分项约 0.09～0.12 ms 是无人脸跳过路径，不是双模型推理速度，不能作为单脸加速结论。

旧 10 月 26 日单脸回放 `replay-01.json` 中完整处理约 693.87 ms；两次 PAD 主机调用约 75.21 + 79.02 ms，其中 SDK 会话准备约 56.60 + 50.91 ms。这说明防伪成本不只是 PS 裁图。该记录是历史样本，不是本次新实拍，也没有据此声称模型内核已提速。

正式网页累计收到 51 份更新结果，截图时显示“未检测到人脸”，总耗时 0.37 秒（人脸 0.37 / 防伪 0.00）；0.00 是未检测到人脸的跳过路径。最终健康检查 ready，录像 source_ready=true、error=null、mode=off。证据为 `browser-check.json`、`shared-panel.png` 和 `final-health.json`。
