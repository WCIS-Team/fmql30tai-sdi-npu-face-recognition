## 原因核查与实现

### SDK 会话

当前 `wcis_owner_kernels.hpp` 原先每次调用都创建 Session、配置后端、apply，然后释放。双脸需要额外四次 PAD 调用，会重复付出会话准备成本。

读取当前学校服务器 SDK 的 `icraft-xrt/core/session.h`、`device.h`、`icraft-backends/zg330backend/zg330backend.h`，并核对项目内厂商 `ps_app/vendor/include/ai_example/multinets_npu_actor.hpp`：该成熟例程在初始化时创建并 apply 多个会话，之后重复调用 forward；等待输出后仍执行 `device_.reset(1)`。这提供了可复用的生命周期范式，但本项目的模型、内存及切换仍需独立验证。

- `ps_app/src/wcis_owner_kernels.hpp`：每个模型惰性创建、配置和 apply 会话，在同一个设备和分配器上复用；保持禁用合并/ETM 优化、OCM None 等原参数。没有并发 SDK 调用。
- 所有输出继续等待 ready、导出、检查有限值和 NPU 绑定；每次完成仍执行一级复位及原帧 guard 检查。没有通过删除完成同步或复位换取速度。
- 回执增加是否复用、创建次数、前向次数和设备活跃分配块/字节统计，用于区分冷请求和热请求、检查内存是否增长。
- `wcis_camera_owner.cpp` 在正常停止且采集/VPU 已排空后，先释放缓存会话，再关闭 SDK。停止收据增加 `sessions_released=true`。
- `WCIS_OWNER_SESSION_CACHE=0` 是候选诊断用的关闭选项，便于同一新二进制进行不复用对照；正式版本启用复用。

缓存增加了驻留设备内存。24 次额外热请求中，最后一次 PAD 调用时，SDK 分配器统计稳定为 40 个活跃块、131,204,256 字节（约 125.13 MiB）。这是当时 SDK 活跃块合计，包含会话和帧/采集等分配；不是模块 BRAM 用量，也不代表完整 PL DDR 容量或实际剩余空间。

为保留原有图片上传范围，缓存只适用于已经测过的 `960×540 / RGB565 / pitch=1920` 摄像头契约。其他尺寸或 BGRX 图片在申请原帧空间前释放缓存，沿用原先单次会话创建/释放方式。返回摄像头时惰性重建；不扩大 FAC1 的 128 MiB 地址窗口或单帧 64 MiB 上限。

### PS 图像展开

- `npu_photo/owner_pad.py` 将整帧多次 NumPy uint16 移位、堆叠，改为 OpenCV 原生 BGR565 转换及 768 字节的逐通道查表。OpenCV 默认低位补零，因此查表明确补回原先的位复制规则，保持 B/G/R 顺序和全部输入值。
- 穷举全部 65,536 个 RGB565 值，展开结果逐字节一致；18 张旧原帧及其 42 份裁图张量也完全一致。
- 最初试用 NumPy 大表直接索引，CPU 单独展开中位约 77.27 ms，慢于原实现约 38.77 ms，因此未采用。随后比较多个实现，最终原生转换加修正的独立展开基准中位约 7.09 ms，原实现约 36.50 ms。
- 独立展开基准不含原图文件读取及 SHA 核验。完整候选回放中的“原图读取＋核验＋展开”单脸中位约 27.74 ms，原版约 43.89 ms，不能把 7.09 ms 当作整段请求耗时。
- 裁图尺度、OpenCV resize、FP32 张量取值、模型融合规则、最多四脸及三秒结果有效期均未改变。

`camera_owner_runtime.py` 和 `serve_photos.py` 同步输出真实会话生命周期，健康接口增加 `npu_session_cache_enabled`。上传照片仍标记防伪未评估，并沿用非缓存的会话方式。
