## 处理与所有权

`ps_app/src/wcis_camera_owner.cpp` 沿用单SDK设备/分配器、现有PL单帧取帧分支和VPU编码，新增两块预分配UDMA缓冲。每块为960×540×2字节；申请后核对64字节对齐、位于既有 `0x30100000..0x38100000` 验证窗口，且两块地址范围不重叠。

每次处理按以下顺序执行：

1. 首次配置PS取帧分支并提交缓冲A；旧PL ImageMake分支保持关闭，continuous模式保持关闭。
2. 明确观察本次请求将DONE清零，避免模型调用跨过整个采集过程后，把上次完成误认为本次完成。
3. 等待A完成，确认该DMA结束；在读取A之前，向另一块空闲缓冲B提交下一次请求。
4. CPU读回A并将其复制到独立原始帧对象，VPU编码也只使用该对象的CPU副本。B可以同时接收下一帧。下次调用才允许重新提交A，此时上次读取已结束。
5. 同一原始帧对象与对应JPEG按编码完成顺序一起发布，只保留最新一份；识别快照仍由原始RGB565进入FAC1/NPU，不解码JPEG作为模型输入。
6. 退出时先等在途相机DMA完成，再释放两块UDMA内存，排空VPU，最后关闭SDK。各轮正常停止均核对请求数=已处理帧数+额外排空1帧，处理帧数=编码帧数。

这是PS软件管理的交替缓冲和提前请求，**没有修改RTL或启用原来写地址相同的连续模式**，也不是PL自主环形DMA。模型执行期间若设备主线程被同步调用占用，仍不能始终按30fps提交请求。

帧时间改用采集请求时刻作为保守下界，字段 `timestamp_basis=capture_request_lower_bound`，另记录完成被软件观察到的时刻。这样模型执行延后读回时，不会用“刚刚读到”冒充“刚刚采到”；沿用源帧新鲜度、boot、PID、帧号、帧令牌和哈希校验。所有NPU及PL命令仍由唯一SDK所有者执行，没有新增并发SDK调用线程。

`WCIS_CAMERA_FPS` 限定1–30，Python构造参数与HTTP服务 `--camera-owner-fps` 传入同一数值；正式配置30。VPU目标帧率随之设置，不再写死5fps。CustomOp模型路径、PL缓存、输入契约和模型阈值未改。

## 网页持续预览

- `serve_photos.py` 新增同源 `/api/camera/stream.mjpg` 与 `/api/camera/status`。MJPEG只发送变化的最新帧，循环检查间隔10ms，不建立旧帧队列；最多4个预览连接，第5个返回503。
- MJPEG线程只读取已发布文件，不使用SDK。服务停止事件会结束视频循环，连接写超时3秒；等待在途识别与HTTP线程退出后，才关闭原生所有者。
- 8091主画面改为持续MJPEG，识别请求单独串行发起。右侧小窗显示最近一次检测的对应帧、框/五点、姓名/未知和“几秒前返回”，旧框不贴到新视频上。
- 暂停检测或只看视频不停止主视频；单次检测不恢复自动循环。后台/隐藏页面会关闭其视频连接并暂停新请求，返回后按原暂停状态恢复；失效来源隐藏实时画面。独立8092预览循环同样改为10ms。
- 页面显示的“采集约多少帧/秒”来自发布帧计数的短窗估算，明确标记为采集率，不能当作浏览器屏幕实际绘制率。
