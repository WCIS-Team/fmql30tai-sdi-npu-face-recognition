# PL 网口预览卸载可行性（2026-10-23）

本轮只做只读核对、带宽计算和方案比较，没有改位流、停止服务、写启动分区或实施新网络通路。建议先验证保留完整视野的 960×540 RGB565、30 fps 经 PL 千兆网口输出，电脑侧转成浏览器可用接口；JPEG 作为后续带宽优化。主要预期收益是减少 PS 逐帧处理和释放 VPU，不预先承诺帧率倍增或 CPU 节省比例。

- 原生所有者消耗约 77.64% 的一个 CPU 核，照片/识别服务约 58.86% 的一个核；4 核系统总忙约 37.36%。不能将进程百分比误读为整机占比。

## 两条方案的带宽

抽样缩小且保留完整视野与裁剪人脸不同。本方案预览保持整幅视野；人脸裁剪只属于识别支路。

按 `宽×高×每像素位数×30` 计算，不含 Ethernet/IP/UDP、应用头和重传：

| 无压缩格式 | 30 fps 像素净带宽 |
| --- | ---: |
| 960×540 RGB565 | 248.832 Mbps |
| 960×540 RGB888 | 373.248 Mbps |
| 1920×1080 RGB565 / 16 位每像素格式 | 995.328 Mbps |
| 1920×1080 RGB888 | 1492.992 Mbps |

因此 960×540 RGB565 有条件适合独立千兆链路，当前百兆链路放不下。1080p RGB565 净数据已接近 1 Gbps，标准 MTU=1500 时加协议开销无法在千兆链路维持 30 fps；1080p RGB888 更超限。该结论针对表内格式，不能推广成所有无压缩格式均不可行。

标准 MTU=1500 的 IPv4/UDP 粗略满包上限为 `1000×1472/1538≈957.09 Mbps`，这里计入前导码、帧头、IP/UDP、FCS 和帧间隙，尚未扣自定义视频头、其他流量或丢包。实际吞吐只会由实际链路验收确定。

此前 1080p PL JPEG 样本中位 139206 字节，若达到 30 fps，像素内容对应约 33.41 Mbps 的 JPEG 净流量；这是按历史样本尺寸计算，**不是 PL 已跑到 30 fps**，复杂画面下字节数会变。计算证据 `bandwidth-calculation.json`。

## 现有 JPEG 核不等于现成的 30 fps 纯 PL 直播

既有 [编码实测](pl-encoder-native-input-20261021.md) 在同一 1920×1080 输入几何下，PL 通路约 20.63 fps，VPU 约 29.34 fps。两者采样、量化和输出画质不完全相同，也不能拿这一 1080p 对照与当前 960×540 预览混为一谈。

当时 PL 试验仍经过 PS 原帧上传和 JPEG 读回：中位上传 3.93 ms、编码及轮询 41.75 ms、读回 0.18 ms。41.75 ms 不能拆解为纯编码时间，但说明不能仅以省去上传/读回就承诺 1080p30。当前 JPG1 实现为固定 1920×1080；要改为 960×540，需要调整和验证尺寸、边界及缓存契约，不能直接喂小缓冲区。

本地 vendor 源码还包含宽度 16 对齐、高度 8 对齐条件，540 并非 8 的整数倍；同一源码对默认 1080 的约束也需与实际冻结实现核对。已有可解码板测不能替代末行像素和 MCU 边界验证。后续应明确合法补边与 JPEG 真实尺寸处理，不能通过裁掉底部像素声称满足“完整画面”。本轮没有据此推断现役 VPU 预览异常。

当前 CPU 路径中还有 RGB565→BGR→I420/NV12 转换及逐帧内存搬运；原生所有者源码 `ps_app/src/wcis_camera_owner.cpp` 可直接看到这些步骤。PL 独立输出能移走这部分预览工作，身份识别的 PS 解码/比对和 NPU 工作仍保留。VPU 是硬件编码器，不能称现状为 CPU 软件 JPEG 压缩。

## PL 网口与网页之间需要什么

板卡背景资料记载完整版有 PL 侧 YT8521/RGMII PHY。`docs/sdi-pl-network-check-20261020.md`、项目顶层和冻结源码没有已接入的外部 PL RGMII 发送通路；当前在线只有 PS eth0。PHY 和插着的网线不自动提供 MAC、ARP/IP/UDP 或浏览器服务。第二路 PS GMAC 借 PL 引出的方案也不等于纯 PL 网络协议卸载。

可行的第一阶段链路：

```text
SDI → PL 抽样（保留完整视野）→ 独立帧缓存 / 分包
    → PL MAC + RGMII + PHY → UDP
    → 同一内网电脑的接收适配程序 → WebSocket / Canvas → 网页
```

第二阶段用 PL JPEG 替换无压缩负载，电脑只重组 JPEG 后提供 HTTP/MJPEG，通常无需重新编码。不能直接把普通 UDP 包交给网页 `<video>` 或 `<img>`。Chrome 官方说明 WebTransport 是 HTTP/3 上的协议，并非通用 UDP socket；若坚持 PL 网口直接面对浏览器，则需进一步实现浏览器支持的 HTTP/TCP 等协议栈，工作量和资源均增加。[Chrome WebTransport 文档](https://developer.chrome.com/docs/capabilities/web-apis/webtransport)

已有可复用网络案例包括 [verilog-ethernet](https://github.com/alexforencich/verilog-ethernet)：RGMII MAC、ARP/IP/UDP 组合及板级示例。上游已声明停维护，后继 [Taxi](https://github.com/fpganinja/taxi) 有 RGMII MAC 等组件，许可证与旧库不同。只将其列为选型输入，尚未选定、下载集成或证明适配 FMQL/当前 Vivado。Arty 等例程不能直接套用本板 PHY 配置、引脚和时序。

## 性能预期与验收顺序

960×540 原帧方案的目标是保住 30 fps 输入节奏、减少 PS/VPU 负担；当前板端发布已约 29 fps，帧率提升空间很小。采用 JPEG 的收益主要是降低网口与接收端数据量；是否降低端到端延迟取决于帧缓存、编码、网络和显示排队，必须实测。

下一步应先完成已知板型/原理图/约束与 PHY 初始化核对，在仿真及离线实现中复用 MAC/UDP 案例，再验证 PL 网口固定数据的完整性、序号和千兆有效吞吐，之后接整幅视频。本轮仅建议顺序，没有执行新位流部署；后续候选上板需保留现役镜像、正常排空当前所有者并安排可恢复的对照验收。

视频支路必须有明确 CDC、帧所有权、缓冲和整帧丢弃策略：网络阻塞不能反压 SDI，也不能堆积旧帧；不能让无界发送消耗全部 DDR 带宽并拖慢 NPU。识别支路需保留自己的原始帧，不从有损预览重新取图；结果框与预览按 frame_id/时间戳绑定。预览 30 fps 不等于识别 30 fps。

验收至少比较同一画面、同一分辨率下的 PS CPU、VPU 使用、板端/接收端帧率、帧龄及上界、丢帧和识别延迟；使用独立场次和并行识别负载。新的 PL 资源及时序代价未综合/布线，不能预报 LUT、BRAM、Fmax 或具体节省比例。
