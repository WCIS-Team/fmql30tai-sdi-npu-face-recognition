# PS 事件录像与网页接入（2026-10-26）

用户确认先使用现有 960×540 VPU 压缩画面打通录像，并明确标注来源；后续 PL JPEG 接入另做。当前实现不调用独立 SDK、不申请 PL DDR、不重新布局布线或修改位流。现役人脸/PAD/预览所有者保持运行。

## 实现

- `npu_photo/recording_service.py`：独立 PS Python 服务，读取现役 `Frames` 发布接口的完整 JPEG。验证当前 boot、PID、session、帧新鲜度和来源；只接受 960×540 的摄像头 VPU 路径，不将测试图或 PL 预览冒充此来源。
- 自动模式后台请求现有 `/api/recognize-camera`，复用原单所有者识别与防伪流程，不依赖网页保持打开。任意人脸均触发，包括陌生人和多人；不要求身份匹配或防伪通过。过期、跨 session、重新启用前的结果不触发。遇到 409 busy 等待下轮，状态报告检测结果年龄，超过 5 秒明确显示触发不可保证。
- 默认最多 2 秒压缩帧预留；无新人脸结果后延续 5 秒。识别响应不是瞬时检测，不能保证画面一出现人脸便触发。当前使用完整识别接口而非新增轻量检测专用接口。
- 每 60 秒或 256 MiB 分段；手动、自动事件切换和采集 session 变化分别隔开。写盘独立线程，队列上限 16 MiB/600 帧，预留缓存上限 16 MiB/300 帧；另有单帧在途开销。队列满丢弃新帧并计数，源帧号跳跃另外计数，不能把队列零丢帧等同采集绝对无漏帧。
- 写 `.mjpeg.part` 和 `.frames.jsonl.part`，完成时 fsync 后改名，最后提交 `.json` 完成记录。只向网页列出已提交录像；异常残片保留，不冒充完整录像。当前正在写入的分段不算异常残片。
- 独立 eMMC 目录 `/mnt/wcis-emmc/wcis-face/recordings`，校验挂载 UUID 与设备，禁止掉挂载后回落 SD。录像配额 4 GiB、磁盘预留 512 MiB；达到限制停止并保留已有录像，不自动删除。写入错误锁定为故障，检查后重启服务再恢复。
- 格式为 **JPEG 帧连续拼接的原始 MJPEG**，索引保存 offset/length、boot/session/frame_id、采集单调时间和接收 UTC 时间。采集时间沿用现役 `capture_request_lower_bound`，不是曝光精确时间。无音频、不是 MP4、不承诺恒定帧率；播放器单独打开 MJPEG 可能采用自己的帧率，时间还原应读取索引。

## 网页与部署

- `recording_panel.html`：自动/手动/停止控制、运行状态、容量和丢帧信息、最近 50 段列表、录像及索引下载，显式标注 VPU 来源。
- `recording_embed.js`：在现有主页面摄像头区域之后插入独立录像页面。录像接口在板端 8093，主页面仍为 8091。跨网络访问时两个端口均需可达；没有改已有网络或认证设置。
- `camera_panel.js`：后台检测与网页竞争现有单请求识别接口时，409 改为等待重试，不再把忙碌当作检测故障；连续网页请求间隔 250 ms。
- 服务 `wcis-face-recording.service`，开机进入自动模式；网页选“关闭”影响当前运行会话。关闭网页不会关闭后台服务。服务进程有 192 MiB 内存限制；退出排空写盘队列并保存收尾状态。它不拥有硬件设备，重启只影响录像。
- 板端代码/证据：`/root/wcis-face/candidates/recording-20261026`；网页修改前副本在 `web-backup/`。原正式应用、模型、人员库入口、BOOT 和摄像头所有者未被替换。
- `rollback.py` 可显式停止/禁用录像服务并恢复网页副本，先检查网页仍匹配本次部署，保留全部录像，不停止硬件所有者。只做语法检查，未实际执行回退演练。

## 验证与边界

13 项本地测试覆盖自动触发/预留/延续、多人/无人、过期和跨 session 拒绝、重新启用前结果拒绝、重复帧、切换采集会话、缓冲上限、分段/索引/退出排空、写盘/fsync 失败、配额/磁盘预留和挂载缺失。原网页视频独立播放、暂停/单次识别和人脸框回归通过。

首轮板端实际摄像头录像 419 帧、3 段，逐帧解码为 960×540，索引偏移、长度和下载内容校验通过，队列丢帧为 0。测试期间原硬件所有者 PID 545、session `la9md829` 保持不变。后台自动检测取得同帧无人脸结果；不是人工标注的真人触发验收。

首次较长并发检查因测试脚本未处理网页并发导致的 HTTP 409 中止；录像服务本身未报错。保留 `final-check-first.json`，后续脚本按已有接口的忙碌契约限次重试。另修正录像列表误将正在写入的两个 `.part` 文件提示为异常残片的问题。

正式 60 秒配置追加实录 2178 帧，分为 1772 帧/59.967 秒和 406 帧/13.700 秒两段；写盘队列丢帧和源帧号跳跃均为 0，队列峰值 386018 字节。期间 7 次现役识别/PAD 接口检查通过，均为无人脸，不当作实际防伪推理吞吐证据。关闭网页期间录像继续。

对正式目录全部三段（含首个因测试忙碌中止的 1399 帧录像）共 3577 帧逐帧解码检查通过；加首轮 419 帧，共检查 3996 帧真实摄像头 JPEG。追加验收脚本含解码共耗时 189.54 秒，超过本机 SSH 等待的 180 秒而报通信超时；重新连接确认板端验收已经正常结束、`final-check.json` 为 passed，自动模式已恢复。没有把通信超时误判成录像失败，也未重复运行硬件任务。

后台浏览器验证了主网页嵌入入口、手动开始、停止、恢复自动模式以及实际文件列表。当前电脑直接访问板端 HTTP 返回空响应，验证使用临时仅本机监听的 SSH 转发，未改变板端网络设置。证据为本机 `D:/yzd/tmp/face-recording-20261026/final-check.json`、`final-audit.json` 和 `recording-page.png`。
