# UYVY→VPU 续查：隔离触发条件与分时原型（2026-10-29）

## 结论

本轮在上一轮停帧定位上继续做差分试验，**已跑通严格分时的真实 1080p 原型，但尚未唯一定位底层硬件/驱动机理，也未部署新预览版本。** 正式系统仍为优化后的 540p `camera-psopt-20261029`。

当前实测指向：真实采集运行与 VPU 编码重叠时容易失稳；SDK 打开、模型描述加载、采集缓冲分配或采集寄存器设置单独存在，并不足以复现同一失败。停止采集并排空后，已有 VPU 会话仍能继续编码。基于这一观察，进一步建立每轮“采集→排空→编码→排空”的原型，完成约 60.49 秒、602 帧输出，其中前两帧为保存原图预热，后 600 帧来自新的真实采集。602 张 JPEG 均完整解码为 1920×1080；后 600 帧的 SHA256 各不相同，三个保存的原帧/JPEG 对与对应流帧一致。

600 个真实输出 / 完整进程窗口约为 9.92 fps，包含初始化等开销，是有限原型窗口，不是浏览器帧率或长期稳定性保证。没有运行 NPU 推理、身份/防伪并发，没有接入正式网站。不能由此称并行 1080p30 已解决，也不能声称找到了唯一的 AXI、DDR 或固件错误。

## 隔离矩阵

各阶段使用相同已保存的 1920×1080 UYVY 输入和 VPU JPEG 质量 80，除注明外无真实采集。模型阶段只加载 YuNet/MobileFaceNet 描述与惰性权重路径，不运行推理、不 apply NPU 会话。

| 新增条件 | 编码结果 | 结论边界 |
|---|---|---|
| 只打开 SDK | 302/302、正常关闭 | 本窗口未复现，不代表所有 SDK 操作安全 |
| 加载两个人脸模型描述，再打开 SDK | 302/302、正常关闭 | 不能外推到模型推理或 PAD 同跑 |
| SDK 分配两块 4,147,200 字节 UDMA 缓冲，不采集 | 302/302、正常关闭 | 分配本身未复现 |
| 分配缓冲、设置采集寄存器，不触发采集 | 302/302、正常关闭 | 配置本身未复现 |
| 真实采集持续运行，VPU 仍编码固定内存帧 | 输出超时，exit=3 | 编码输入没有换成采集数据；组合条件可影响独立输入的 VPU |
| 先采集两帧并暂停/排空，保持 SDK 与采集缓冲，再建立 VPU | 302/302、正常关闭 | 实际采集发生过，但编码期间无活动采集 |
| VPU 先编码并排空两帧，建立采集后暂停，再恢复固定帧编码 | 304/304、原生正常退出 | 已有 VPU 会话没有必然被一次采集永久破坏；该次恢复正式服务未 ready，另行重启恢复 |
| 高细节合成 UYVY，不打开 SDK、不采集 | 302/302，首帧解码，其余逐字节哈希一致 | 不把近黑色画面通过当作复杂画面证据；不是实时网络性能测试 |
| 每轮真实采集、排空，再编码、排空 | 602/602，含 600 个新采集结果，正常关闭 | 本轮有效分时原型；不是正式部署或长稳验收 |

原保存测试帧经目视检查几乎全黑，因此前一轮约 53.71 dB 的 PSNR 仅支持该低复杂度样本的内容对应，不能代表明亮复杂画面、完整颜色或细节验收。本轮另用确定性高细节 UYVY 字节模式测试编码：302 帧全部具有相同压缩结果，输出共 397,972,882 字节，首帧可解码为 1080p，其余同哈希。该测试包含落盘开销，约 18.27 秒完成，不能拿它宣称复杂画面 30 fps。

SDK/模型/分配三组各约 10～12 秒，均为有限窗口；组合采集组与控制组的进程历史、持续时间不完全相同。结论应写“触发条件已收窄、分时原型通过”，不应写“已严格证明唯一物理原因”。

## 原型实现

所有 C++ 改动只在 `D:/yzd/tmp/uyvy-isolation-20261029/source/ps_app/src/wcis_camera_owner.cpp` 及任务源码副本内，不改生产 C++ 或 RTL。板端探针在 `/root/wcis-face/candidates/uyvy-isolation-20261029`。

复用已有 `TrialCamera` 的版本/SDI 锁定检查、经过核对的寄存器配置、UDMA 窗口、双缓冲、映射与 SDK 读回对照、请求清除旧 DONE 及正常排空流程；YUV422 输出沿用已有 `0x78`/`0x7c` 契约。没有探测猜测 DDR 地址、改引脚或重做位流。

为隔离活动采集，增加 `pause()`，先停止并 join 采集工作线程，再排空其在途请求，保留已分配缓冲；`close()` 在此之后才释放缓冲。配置组不启动采集，暂停组保持分配和 SDK。已有 VPU 会话组先完全取走两个预热输出，再采集/暂停。

最终 live 原型使用 `pull_paused()`：要求采集线程已停止且无在途请求，采集一个可读帧并排空提前发出的下一请求；返回不可变原帧，然后提交 VPU，并在下一次采集前取走编码结果。沿用原硬件检查，没有放宽新鲜度或超时阈值。该实现会采集额外帧但只选部分帧编码，输入请求数/物理采集率不能当作预览输出 fps。最终记录 camera_captured=602、submitted=received=602；其中只有后 600 个编码结果属于本次新图像输出。

`live-result.json` 的父脚本继承了早期暂停组字段 `camera_paused_before_vpu=true`，该描述不准确：live 模式先建立 VPU 会话，在每次实拍编码前确保采集暂停，并非在创建 VPU 前一直没有采集。`camera_dma_enabled=false` 也只应解释为编码阶段没有并行的采集请求，不是本次没有使用 DMA。以 native 的 mode=live、源码调用顺序及 `live-validation-notes.json` 为准，保留原收据不覆盖。

## 输出验证与其他检查

- SDK、模型描述、分配及高细节组分别检查 302 个完整 JPEG 包、单帧解码几何和所有包哈希一致性，结果 `matrix-qa.json`；相同固定输入产生同一结果。
- live 视频流分成 602 张 JPEG，Windows GDI+ 逐帧解码并读取末行末像素，均为 1920×1080；见 `live-decoder-validation.json`。三个保存样本 0/299/599 分别与视频第 2/301/601 张字节一致（零起始索引，扣除两张预热），原帧均为 4,147,200 字节；见 `live-stream-validation.json`。后 600 张 JPEG 的哈希互不相同。
- 只读检查现役 540p 进程的 `/proc/<pid>/pagemap` 与 `/dev/video0` 用户映射，记录的已映射物理页均未落入已知 UDMA 窗口。它只覆盖当时的 540p 用户帧缓冲，不覆盖 VPU 内部 MMU/固件内存，也不能用于宣布 1080p 无任何地址冲突。
- 捕获并发组在 VPU 输出 deadline 后展开异常，仍有采集线程未排空，随后触发 TrialCamera 析构保护。最先出现的是 `PS-memory VPU output deadline`，不能把后续析构保护改写为最初根因。该组没有正常 SDK 关闭证明，按故障启动重启恢复。
