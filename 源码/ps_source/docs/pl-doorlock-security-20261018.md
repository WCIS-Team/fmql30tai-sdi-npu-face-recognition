## 先纠正验收目标

现有照片测试验证的是“这张图像像谁”，不能证明镜头前是真人。
此前照片、静态DDR、SSH视频和合成多人图的功能证据继续有效，但它们不是门锁授权或防照片攻击验收。
前面新增的质量检查、历史检索和登记特征比较属于软件辅助模块，不再作为本团队PL新增功能的主线。

安全缺口是人脸呈现攻击检测（PAD）。NIST对普通二维图像的纯软件PAD已有独立评估，
说明身份识别与呈现防伪需要分别验证；参考[NISTIR 8491](https://www.nist.gov/publications/face-analysis-technology-evaluation-fate-part-10-performance-passive-software-based)。
清晰度、亮度、帧差、眨眼、转头或简单频域阈值都不能直接作为本项目已通过防伪的证据。
本轮没有新增PAD模型推理，当前系统仍不能声称能阻止拿照片或手机回放冒用。

## 适合本团队承担的边界

| 组成 | PL侧工作 | 需要协作或验证的部分 |
|---|---|---|
| 身份识别输入 | 原帧DDR、尺寸/格式处理、五点对齐、对应模型输入数据路径 | NPU模型和PS特征解释已有独立职责 |
| PAD输入 | 按选定模型契约保留原始框或周边区域、缩放及像素精度；与身份输入绑定到同一帧同一人脸 | PAD模型与板端NPU可用性需单独检查，不能由像素统计替代 |
| 缓冲和有效性 | 描述符锁存、地址范围、帧号、换帧缓存失效、错误结果作废、读写所有权 | PS核对会话、帧号/脸索引、结果新鲜度及失败状态 |
| 权限及开锁 | 提供有效数据与错误状态，不自行从姓名/对话生成开锁决定 | PS以身份、PAD、权限和本次会话共同判定；本轮仅交接约束，不写PS门锁策略 |

帧号和缓存失效只能防止工程上的串帧、旧缓存误用，不能辨别纸质照片。
同样，完整DDR读回正确不等于输入来自真人；摄像头拍到照片时，数据通路仍可能完全正确。
不把帧号或像素SHA宣传为物理防伪或恶意注入防护。

## 查到的可复用PAD案例

1. [OpenVINO anti-spoof-mn3](https://docs.openvino.ai/2023.3/omz_models_model_anti_spoof_mn3.html)：
   面向RGB图像的二分类，文档明确128×128输入，原始模型与转换模型的颜色/归一化契约不同。
   原始[上游示例](https://github.com/kprokofi/light-weight-face-anti-spoofing/blob/master/demo/demo.py)从检测框裁图后送入网络，未使用身份识别的五点对齐图。
   它是候选，尚未验证当前iCraft编译器支持或本板执行，不引用其公开数据集分数作为本门锁指标。
2. [Silent-Face-Anti-Spoofing](https://github.com/minivision-ai/Silent-Face-Anti-Spoofing)：
   有可读取的裁图、模型测试及训练代码。其[裁图实现](https://github.com/minivision-ai/Silent-Face-Anti-Spoofing/blob/master/src/generate_patches.py)
   按模型所需尺度从原图扩大检测框再裁切；上游明确实际效果受摄像头及场景影响。
   其裁图契约与上述MN3不同，不混用，也不照搬上游阈值。

当前`model_backend_runtime.py`固定处理YuNet和MobileFaceNet，输入尺寸分别640/112；
没有已经接好的第三路128×128 PAD会话，不能仅增加一个Python角色名就宣称支持新模型。
后续任何模型导出/转换/校准/编译仍按项目约定重新检查学校服务器，使用隔离任务目录；本轮没有启动此类构建。

PAD输入在PL实现前，必须锁定模型版本、原图裁切方式、边界规则、缩放插值、色序、归一化及输出类别含义。
现有仿射采样器的replicate边界是整张原帧边界；若用整帧坐标直接模拟“先裁ROI再resize”，
在ROI上采样边缘可能与参考裁图复制边界不同，不能未经像素对照就复用为PAD输入。
RGB565保留为旧格式兼容，不默认视为与完整8位颜色等价；须验证其对防伪分数的影响。

## PS/NPU协作接口约束（方案，尚未实现）

- 身份结果与PAD结果必须属于同一会话、同一原帧、同一脸索引及对应ROI，避免用甲的真人结果给乙的身份放行。
- PAD未运行、模型故障、输入不完整、超时、帧/脸不匹配时，返回未验证/无效，不能默认当成真人。
- 照片/SSH回放仅用于测试，不因身份匹配成功而自动进入真实门锁授权路径。
- 正常启动、复位和错误恢复后清除上次成功结果；本次结果必须有完成状态和可验证的归属。
- 接入ASR、LLM及PAD后需核对NPU设备生命周期、DDR租约和争用，不能继承当前两个人脸模型的独占短测帧率。

这些是交接要求，不是当前已上线的门锁控制逻辑。

## 本轮实际PL优化

修改`D:/renlianshibie/fpga_project/rtl/wcis_face_customop.v`的native DDR读缓存：

- 由一条64字节缓存改为两条全相联缓存；命中时维护LRU，未命中优先使用无效条目。
- 保留单个在途读事务、原有CDC握手及64位AXI侧接口，不预取、不增大地址访问范围。
- 双线性采样反复访问上下两行时可以同时保留两行对应的DDR块，减少往返读取。
- 每条新命令和复位均使两条缓存失效，避免物理地址复用读到上一帧。
- 没有修改采样坐标、像素插值、寄存器布局或模型张量契约。

优化前源码保存在`D:/yzd/tmp/face-pl-cache-20261018/before/wcis_face_customop.v`。
新增可复跑对照脚本`D:/renlianshibie/fpga_project/scripts/verify_face_line_cache.py`，
所有生成文件在私有任务目录，不修改Downloads原案例、case工程或安装工具。
脚本对同一像素golden分别运行原版与新版，包含两条缓存均被使用后在同一地址更换整帧的回归。

### 仿真结果

7组原版/新版逐像素对照全部通过，每组使用同一输入、同一golden及相同随机种子；
覆盖背压、异步GP/HP时钟、原厂adder保留、非法描述符拒绝、部分字节写保护和换帧缓存失效。

| 用例 | 原版native读次数 | 新版native读次数 | 减少比例 |
|---|---:|---:|---:|
| 特制双行双线性采样，1024像素 | 2176 | 272 | 87.5% |
| 旋转/边界/补边 | 232 | 50 | 78.45% |
| 公开照片112×112对齐 | 24912 | 7079 | 71.58% |
| 奇数pitch身份变换 | 8 | 8 | 0 |
| RGB565奇数pitch | 5 | 5 | 0 |
| 同址换帧小用例 | 2 | 2 | 0 |
| 1080p检测输入画布 | 43200 | 43200 | 0 |

特制双行用例还在两条缓存均已填充后，用相同物理地址换入另一整帧，并逐像素验证新输出，
两版均通过。另通过包含JPEG的`wcis_recording_customop`运行双行、换帧和实际照片对齐3组回归。
这3组不同时启动JPEG编码任务，不能代替JPEG/NPU并发压力验收。

1080p检测用例以整数采样为主，没有获得读次数或该仿真计时收益，不能宣传整条识别链路统一提速。
所有读次数来自仿真模型；板端实际等待、DDR仲裁、NPU、PS转换均未在本轮重新测量。
脚本中的`job_ns`只代表TB内部固定测量窗口，不是完整板端请求时延，本报告不据此承诺实际帧率。

## 真正的防照片验收还需要什么

必须用实际SDI摄像头采集真人和攻击呈现；仅把JPEG文件直接送入模型不能代替相机前的攻击测试。
至少覆盖不同打印照片、手机/平板显示静态人像和播放视频，并覆盖距离、角度、亮度和背景变化。
记录真人被拒与攻击被接受的次数/比例，分别看打印照与屏幕回放，阈值确定与最终测试使用独立数据。
有限样本零误放仍不是对所有攻击的保证；高安全目标后续需评估额外传感器或独立认证因素。
本轮未改摄像头硬件、未接开锁执行器、未声称完成上述安全验收。

## 人脸支付方案参考补充（2026-10-18）

本节是用户提出“参考人脸支付”后进行的公开资料核查，不是新模型构建或PAD实现记录。

### 官方资料核实结果

- [微信刷脸支付产品文档](https://pay.wechatpay.cn/wiki/doc/wxfacepay/product/)明确说明使用指定3D安全摄像头及通过认证的硬件，并将识别、安全技术和风控结合。
- [微信设备接入文档](https://pay.wechatpay.cn/wiki/doc/wxfacepay/open/open-access.html)要求摄像头集成测试、设备检测；更换摄像头也需要报备和对应测试。不能把“装了某个防伪模型”视为这些要求已经满足。
- 微信[软件接入文档](https://pay.wechatpay.cn/wiki/doc/wxfacepay/open/software-join.html)另有指定2D摄像头用于门禁的场景，不能据此推断任意2D SDI摄像头具备线下支付同等安全能力，也不能反向声称所有人脸应用都必须使用3D。
- [支付宝公开说明](https://render.alipay.com/p/c/jygb47sq)介绍活体检测，并说明手机刷脸付与已验证设备有关；该页不是可复现的算法/模型实现，不能据此保证自研系统的防伪效果。
- [FIDO生物识别要求](https://fidoalliance.org/specs/biometric/requirements/Biometrics-Requirements-v4.0-fd-20240522.html)将身份匹配与呈现攻击检测列为不同评估项目，可借鉴分别测试误认、误拒和攻击放行的思路。本项目尚无相应认证，不能宣传认证或支付级安全。

### 对当前普通SDI方案的判断

可以实现并验证“现有身份识别＋RGB PAD”的实验原型；不承诺普通SDI经软件改造即可达到支付设备的防伪水平。
模型候选仍需当前iCraft工具检查、学校服务器转换/编译及真实板端验证；本轮未执行这些步骤。
保持普通SDI时，优先评估既有RGB模型，按实际摄像头采集真人、打印照、静态屏显及视频回放，报告分类结果及误拒/误放。
现有照片身份测试保留作为身份回归，不被用作PAD有效性的证据。

对本团队PL部分可复用的设计是：从受控原帧产生符合模型契约的输入，保留必要的完整8位颜色与周边区域，
将PAD与身份输入绑定同一帧/同一脸，并明确错误和完成状态。当前缓存优化仅改善访存，未增加PAD能力。
识别和PAD的模型推理由NPU端协作，PS负责最终权限及本次验证状态；本团队不扩写对话和开锁业务。

后续若增加红外/深度模块，需要先核对接口、同步、标定与本板SDK适配，不能假定支付SDK支持当前FMQL30TAI Linux环境。
仅接上3D模组也不能替代完整安全测试。现阶段默认沿用用户已确认的普通SDI摄像头，不擅自更换硬件。

本轮只进行了资料核查及文档补充，未改RTL、位流、模型、服务或实际门锁状态；背景站仍连接被拒绝。
