## 注入点和可验证范围

厂商案例已有 VTC 灰度测试图；本地入口见 `ps_app/src/wcis_camera_preview.cpp` 的
`--run-vtc-test`，参考连接见 `case/rtl/ps_ai_peripheral.sv` 的 `u_vtc`。
以前厂商 BOOT 的测试结果见 `board-factory-restore-20261014.md`，不能当作当前位流
或完整人脸链路的最新验收。本轮没有再次启用 VTC、SDI 或修改其寄存器。

本轮需要有脸的输入，因此采用已有 SDK 帧租约上的静态 DDR 回放：

1. 仅初始化时 PS 解码、整理并上传一次原图至 SDK 分配的 PL DDR。
2. 暂时移走 PS 输入像素文件，并将再次解码、原图打包入口替换为报错检查。
3. 保留相同帧租约，反复执行 PL 缩放、NPU 检测、PS 解码框与求对齐参数、
   PL 五点对齐、NPU 特征提取和缓存特征比对。复用现有模块及部署二进制。
4. 全部回放结束后恢复验证副本，完整读回 DDR 原帧逐字节校验，最后关闭工作进程并释放锁。

这是同一静态帧的多次处理，不伪造新采集帧号。回放序号与租约帧身份分开，
全程持有完整硬件独占锁。没有真实相机时钟、持续写入、双缓冲、新帧发布/归还、丢帧或队列测试。
未来真实摄像头/PL 图像源直接写入该类缓冲后，才可省掉每帧 PS 原图准备；
仍须确认 RGB565/BGRX 格式、pitch、地址映射、完成信号和所有权。

## 实测结果

使用同一张板端已有的 640×1277 单人图片，不导出图片、人员姓名或特征向量。
同一套驻留模型先预热，正常照片路径测3次，回放预热1次并测10次，之后正常路径再测3次。
此为前后分组对照，不是两版逐次交替、长期负载或实时吞吐基准。

| 计时 | 中位数 | 范围 |
|---|---:|---:|
| 正常照片处理链路，6次 | 682.7 ms | 677.5～695.1 ms |
| DDR原帧回放处理链路，10次 | 515.4 ms | 514.3～646.7 ms |

同图处理中位减少约24.5%，一次性原帧准备为360.7 ms，不计入回放耗时。
正常链路的 `elapsed_ms` 从 PL 准备阶段开始，不包含前面的照片读取/解码、请求检查、
模型CPU进程启动和完整HTTP；回放同样仅计处理链路，不能用此结果宣称网页已降至515 ms。
保留实际646.7 ms样本，不据中位数推断尾延迟或连续摄像头帧率。

回放各阶段中位数：缩放及回读239.3 ms、检测调用135.6 ms、检测输出解码7.3 ms、
对齐27.2 ms、识别调用99.8 ms。阶段中位数之和不要求等于总耗时中位数。
缩放路径仍有 SDK 打开/关闭、输出初始化、PL 执行和回读；
原来约400 ms的准备阶段包含这些工作，省掉原图上传并不等于省掉整段准备时间。
仍有PS张量转换、临时张量传递、对齐参数计算及特征比对。

10次测量和1次回放预热的检测/特征模型原始输出SHA、框、512维归一化特征与比对分数
均与正常路径完全一致。源图只构建、上传各1次，后续各次均从DDR引用，源文件缺失期间仍成功。
最终完整原帧逐字节校验通过。
