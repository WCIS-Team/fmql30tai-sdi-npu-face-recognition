## 4. T1：延迟测量方法与基线

### 4.1 主指标：摄像头看到事件到预览显示事件

推荐用一台外部相机同时拍到源事件和预览屏幕：在 SDI 摄像头视野内放置可切换明暗的物体/光源，让外部相机同时看到它以及网页中的对应预览。网页只放大实时视频，不把检测图当作视频。也可用同一外拍画面内的源计时屏与其预览影像计算差值。

- 每个条件拍摄至少 30 次明确变化，间隔至少 2 秒；固定相机、网络、浏览器、窗口大小、分辨率和现场光照。源计时屏方案记录刷新率和曝光限制，避免递归拍屏。
- 外拍建议至少 60 fps。按事件在源与预览第一次可辨认的外拍帧号计算 `延迟_ms = (显示帧号 - 源帧号) × 1000 / 外拍fps`。记录外拍实际帧率/时间戳，变帧率素材按帧时间戳计算。60 fps 的单帧间隔约 16.7 ms，需记录两端判读和屏幕扫描带来的误差，不能报告虚假的毫秒精度。
- 不能看清的事件标明原因；超时/丢失事件单列并计为失败，不静默删除。逐样本保存源帧、显示帧、差值、负载和素材位置。p95 使用排序后第 `ceil(0.95×N)` 个样本，p50 使用中位数，另列最大值与失败数。
- 没有外拍条件时，先做下面的诊断测量，但将“端到端验收”标为待测，不能用浏览器录屏或 API 时延代替。

### 4.2 辅助指标：定位等待发生在哪里

记录捕获请求/完成时间、真实输入帧日志、编码/分片发布时刻、段时长、HTTP 取段耗时、浏览器 `currentTime` 与 `buffered.end`、重连和卡顿事件。优先从已有日志及接口采样，避免为了测量逐帧刷盘或添加正式页面功能。

板端单调时钟与浏览器时钟不能直接相减；媒体 PTS 也不是墙钟。若建立映射，记录方法、时钟偏差/漂移与误差，按真实帧索引/片段 capture metadata 对应，不能仅凭“名义 30 fps”外推。播放器距缓冲末端、末段新鲜度和光学端到端延迟分别汇报，不能随意拼接不同时间点的快照。

### 4.3 对照条件

先完成当前 H.264 基线。只有确认旧 JPEG 的软件、模型接口和数据格式仍兼容，并具备正常关闭与回退条件时，才做旧版同条件对照；不能直接重跑历史部署脚本或并行打开第二路硬件 owner。旧版无法安全复现时，记录“旧版数值对照缺失”，不阻止测量当前版，但不得声称已经恢复到旧版水平。

## 5. T2：播放器候选 A

入口为 `lan_stream/h264_player.js`，复核真实 `--site` 及服务分发文件，避免只改未被使用的副本。

1. 保持编码与封装配置不变。起播选最近可独立解码的完整段，并在 SourceBuffer 成功追加后定位到合法可播放范围；不能跳到尚不存在的数据或非独立解码入口。
2. 缩小允许的积压，评估受限加速或必要时 seek 的效果。候选先试目标距已缓冲末端约 0.2～0.4 秒，触发追帧阈值约 0.8～1.0 秒；这是实验参数，不是已验证最优值。1 秒分片下余量过小可能反复断粮，必须记录卡顿后再决定取值。
3. 调整起播和追帧分两步留证；初轮保留轮询周期，只有测得轮询等待占比明显时才单独评估更短周期及请求负载。不盲目缩小所有缓存。
4. 补充有意义的播放器行为测试：缓冲为空、非零起始 PTS、合法 seek 范围、缺段/异会话、网络延迟、暂停恢复、追帧频率有界和资源释放。制定时没有 `tests/test_h264_player.cjs`；11-02 已新增并通过16项离线行为测试，不代表浏览器/板端低延迟验收通过。
5. 同条件复测，保留候选 A 的参数、散列、延迟分布及卡顿数据。若分片等待仍主导且未达目标，进入 T3。

## 6. T3：短分片候选 B

入口为 `lan_stream/external_h264.py`；相依模块是 `h264_media.py`、`h264_fragments.py`，以及独立录像服务中的实际部署副本。

1. 保持 VPU H.264、960×540、无 B 帧及现有准入保护。先尝试 GOP=15 / 约 0.5 秒分片，再根据测量尝试 GOP=6 / 约 0.2 秒；每次仅一个候选。参数只是试验提案，必须通过板上实际 FFmpeg/VPU 输出核实。
2. 只调 `hls_time` 不保证短片段；核对实际 IDR/关键帧间隔、各段实际时长与独立解码能力。驱动若不接受参数或输出不符合，停止该候选，不以命令返回零认定通过。
3. 窗口按秒核算：现有列表 12 段缩成 0.2 秒段后仅约 2.4 秒；同时检查 `h264_media.py` 最多 16 段、读端初取两段、录像预缓冲/轮询和缺段检测。不能照搬“12 段”“最后两段”而悄悄缩短录像前录时间。必要时调整有界窗口及相关上限，保持按时间表达的既有语义；记录内存/请求成本。
4. 对已发布段逐段核对样本数、采集索引和时间单调性；正常结束后的 MP4 全帧解码、可定位回放、Range 读取与旧 JPEG 兼容必须通过。不将媒体 PTS 混作原始采集时间。
5. 缩短 GOP 可能增加码率、降低同码率画质，短段可能增加 HTTP/文件处理与 CPU 成本。保持同场景和同码率先比较运动、人脸细节、卡顿与负载，不靠黑画面、小文件或平均 SSIM 单独判画质达标。
6. 沿用现有 `lan_stream/test_external_h264.py`、`test_h264_fragments.py`、`test_vpu_live_server.py` 及 `tests/test_recording_service.py`、`test_recording_library.py`；涉及当前压缩兼容时运行 `test_recording_compression.py`。按 [维护计划](maintenance-plan.md)配置依赖并逐进程运行；平台跳过项必须明确记录，需要 Linux 的用例在隔离环境补测。只扩展与变更相关的测试。

## 7. T4：验收矩阵与通过门槛

以下数值是本 SOP 制定的**工程目标/停止门槛，不是既有实测结论或用户原先指定指标**。执行前写入任务记录，不能测完后放宽门槛并称原目标通过。

| 验收项 | 测试安排 | 通过条件 |
|---|---|---|
| 暖态端到端延迟 | 仅预览、预览+识别/PAD、预览+识别/PAD+录像，各至少 30 个外拍事件 | 暂定各条件 p50≤300 ms、p95≤500 ms；无未显示事件。未达到则保留测量，不称低延迟验收通过 |
| 与旧体验对照 | 旧版能安全复现时同条件实测 | 候选 p95 不高于旧版 p95 加测量误差；缺旧版证据时不能写“与原来一样” |
| 起播与恢复 | 至少 5 次页面重开、5 次客户端断开/恢复、5 次页面后台/前台切换 | 局域网可用后 3 秒内出现新鲜画面，无旧会话回放；记录每次实际值。只断测试客户端，不改板端网卡配置 |
| 连续流畅性 | 最终候选连续 30 分钟：三种负载各 10 分钟 | 无硬件隔离、进程异常、媒体错误或非人为重连；暖态无超过 500 ms 的冻结。用连续运动/计时画面及可用浏览器事件判读，不用静态画面掩盖冻结 |
| 帧率与资源 | 各窗口记录源帧、实际呈现帧/可用计数、CPU、RSS、队列、码率 | 源帧均值至少 28 fps；源帧率与呈现帧率分开。记录追帧丢弃数；相对同负载基线 CPU 增量超过 0.2 核或 RSS 增量超过 64 MiB 时暂停发布并说明取舍，不以优化为名无限增耗 |
| 模型与同帧归属 | 固定原帧前后原始输出对照及至少 10 次现场请求 | 模型输出符合既定一致性契约；boot/session/frame/source hash 对应，无串帧或过期结果误用。PAD 未校准状态保持不变 |
| 录像兼容 | 正常光照运动场景，新建跨至少 2 个既有 60 秒分段的样本并正常收尾 | 全帧解码、索引、时间轴、Range/回放通过；前录/后录语义不退化。保留原片和已有数据，不删除验收素材 |

30 分钟只称“30 分钟有限持续验证”，不外推全天稳定。录像模式、闲时压缩和其他任务都是影响变量：按用户执行时的设置记录；对照时若需要暂时调整，记录前值、调整范围与恢复结果。不得杀掉其他任务制造低负载成绩，不能认为低优先级压缩绝不与识别重叠。

- 编码/owner 需要重启时，先正常结束录像并收尾，按既定顺序停止视觉服务；验证本次 PID/boot 的 SDK 正常关闭回执及进程退出后再切换。普通应用更新不停止会卸载 eMMC 的存储服务。
- 使用有界就绪检查确认健康、模型缓存、帧推进和录像输入，再核对浏览器实际播放与正式入口延迟。API ready、30 fps 或全帧解码均不能替代延迟验收。
- 出现采集超时、MVX watchdog/MMU 错误、隔离标记、源帧不推进、模型原始输出差异、段丢失/解码失败、原片损坏或无法正常收尾，立即停止该候选，保存证据；不得自动删除隔离或无限重试。
- 回退只恢复本次冻结的正确版本及配置，保留新旧录像和人员数据。硬件无法证明正常关闭时，不自动启动旧版碰运气；按故障隔离流程安排恢复。回退后的健康、实际视频、模型与录像兼容另验。
- 若短分片仍达不到目标，明确写“当前方案未达标”。再评估恢复经过复核的旧 JPEG 方案或替换传输机制的成本；不在本轮直接引入另一套推流协议、第二路硬件编码或降低安全检查。
