# 02 坑与排查（部署过程实录，2026-11-04）

按踩到的时间顺序。每条：现象 → 定位 → 解法。

## 坑#1 plink 首连挂死（Windows 侧）

- **现象**：`echo y | plink -ssh -pw <redacted> root@113 "命令"` 永远无输出，120s 超时。
- **定位**：plink 的「缓存主机密钥 y/n」提示走 Windows 控制台 API，**管道喂不进去**，进程挂在那等键盘。
- **解法**：`plink -batch -hostkey SHA256:xxxx -pw <redacted> …`（先 `ssh-keyscan` 拿指纹）。之后全程改用 OpenSSH + key，不再用 plink。

## 坑#2 OpenSSH 无 TTY 时密码交互挂死

- **现象**：`ssh root@113` 不带 `-i` 时整条命令挂 90s 无输出，像板子死了。
- **定位**：密码提示需要 TTY，无 TTY（脚本/管道环境）时 ssh 卡在 password prompt；`-v` 加 `-o BatchMode=yes` 立刻得到 `Permission denied (publickey,password)`，证明板端 sshd 本身是好的。
- **解法**：脚本里一律 `-o BatchMode=yes`，让失败立刻显式暴露，绝不静默等待交互。
- **教训**：同一台板「连接挂死」可以是本机工具行为，不一定是板子问题；先用 BatchMode 分离「网络问题」和「交互问题」。

## 坑#3 公钥装了却被拒：/root 属主是 fmsh（厂商镜像怪癖）

- **现象**：authorized_keys 写入成功，`ssh -i` 仍 `Permission denied (publickey,password)`。
- **定位**：板端 `journalctl -u ssh` 一行：`Authentication refused: bad ownership or modes for directory /root`。
  出厂镜像里 `/root` 属主竟是 `fmsh:fmsh`（755），sshd StrictModes 因父目录属主不对直接拒绝公钥。
- **解法**：`chown root:root /root`。改完 key 立即可用。
- **注意**：任何「装了 key 连不上」先看服务端日志，本条与密钥本身无关。

## 坑#4 出厂 DTB 隐藏 eMMC（lsblk 看不到 mmcblk1）

- **现象**：出厂态下板上只有 SD（mmcblk0），`board.example.json` 要求的 eMMC 数据分区（mmcblk1p1）不存在；`dmesg` 里只有一条 dwmmc 控制器。
- **定位**：拆 DTB 对比（Python 手写 FDT 解析，板上没有 dtc）：厂商 `fmqlmp-verify.dtb` 把 `dwmmc@e0044000` 设为 `status: disabled`；提交包 DTB 同节点为 `okay` + `non-removable` + `no-sd/no-sdio`（= eMMC）。**两份 DTB 除该节点外无任何差异**。
- **解法**：无需处理——换上提交包 BOOT+DTB 后 eMMC 自然出现（29.1G Y2P032，里面还是 10 月的人员库）。
- **教训**：`board.example.json` 的 mmcblk1p1 假设只在「项目 BOOT」下成立；给空板写文档时应提示「出厂 DTB 下看不到 eMMC，属正常」。

## 坑#5 换 BOOT 重启后 ~12 分钟网络不可达（根因未定位）

- **现象**：换 BOOT + `systemctl reboot` 后，ping/ARP 全无响应约 12–15 分钟；期间全网段扫描也没有新设备。
- **板端日志视角**：内核 20:39:16 eth0 link up、20:39:18 DHCPACK 拿到 192.168.1.113，之后无任何 link down/网络重启记录；boot 1min34s 完成。20:51:22 出现第二次 DHCPACK（**新的 dhclient 进程 PID 260**，非 renew 语义），此后外部立即可达。
- **已排除**：DHCP 换 IP（板端始终绑定 .113）；IP 冲突；DTB 网络配置差异（两版 DTB ethernet 节点一致）；重复重启（uptime 连续）。
- **未定位**：板端自认一直在线、外部却不通，L2 路径上发生了什么无法从两端日志还原。
- **处置**：等。若再遇到，优先怀疑交换机/AP 的 ARP 学习或板端 PHY 与项目 PL 位流的初始化时序，可在串口下抓。
- **教训**：换 BOOT 后的等待窗口要按「≥15 分钟」预留，别提前判定变砖。

## 坑#6 pkill -f 自杀（老坑重踩）

- **现象**：想杀板上一个 dd，`pkill -f 'dd if=/dev/mmcblk0p1'`——当前 ssh 会话（bash -c 命令行里含同样字符串）被自己一起杀掉，后续命令没执行、无回显。
- **解法**：`pkill -x dd` 精确进程名，或换个不含关键字的命令行；清理用独立的下一条命令补做。

## 坑#7 unattended-upgrades 常驻吃资源 + 抢 apt 锁

- **现象**：出厂态板子 load 1.55，`unattended-upgrade` 单进程 46% CPU + 194MB RSS（全板 1GB 内存），并且 apt 操作期间可能锁冲突。
- **解法**：部署前 `systemctl stop unattended-upgrades`。本次实测 apt 未实际撞锁，但内存余量明显改善。

## 坑#8 FAT 启动分区整分区 dd 镜像不值得做

- **现象**：想给 1GB FAT 分区做 gzip 镜像当兜底，实测 dd 读速仅 ~1.8MB/s，且 FAT 未用空间是删除残留垃圾（gzip 压不动），预计 10 分钟+。
- **解法**：只做文件级备份（9 个文件 40MB，`cp -a` 秒级）。恢复时读卡器重格 FAT 拷回即可，效果等同。
- **注意**：vfat 挂载默认 `codepage=437,iocharset=iso8859-1`，纯 ASCII 文件名不受影响。

## 坑#9 校机 bash --norc 下 PATH 为空

- **现象**：`bash --noprofile --norc script.sh` 第一行 `dirname: command not found`。
- **定位**：MSYS2 的 bash 在 --norc 下不继承任何 PATH，`/usr/bin` 里的基础工具全找不到。
- **解法**：脚本第一行显式 `export PATH="/d/yzd/MSYS2/usr/bin:/d/yzd/MSYS2/mingw64/bin:$PATH"`，并把任务目录硬编码（不依赖 `$0`/dirname）。

## 坑#10（本会话工具链）Git Bash 下多行 ssh 命令的引号

- **现象**：远程脚本里 `${unit##*/}` 这类参数展开若直接放进本地双引号字符串，会被**本地** shell 先展开成空。
- **解法**：多步远程操作一律先写成 `.sh` 文件 → scp 上去 → `sh /root/xxx.sh` 执行。板端和校机两侧都适用；这也是本项目 AGENTS.md 的既定规矩，本次全程照做。

## 非坑但重要的事实

- 出厂 rootfs 的 `Image`、`uEnv.txt` 与提交包**逐字节相同**——换 BOOT 实际只需覆盖 2 个文件（BOOT.bin、fmqlmp-verify.dtb）。
- 出厂 rootfs 无 curl/sshpass；python3 3.8.10 已带；apt 源为中科大 ports 镜像 + armnn PPA。
- 板子走**有线以太网**（eth0, fmql-dwmac, 100Mbps 全双工），不是 WiFi；此前 ARP 里看到的随机化 MAC 是其他设备干扰判断，别用它猜接入方式。
- eMMC 上的 10 月人员库（LABEL=WCIS_FACE）在恢复出厂后完好，`render_install.py` 渲染的新空库与旧库的 pipeline 指纹同源（模型文件未变）。
