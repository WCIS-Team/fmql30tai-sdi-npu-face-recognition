## wcis_camera_owner 的比特差异：已查清，是路径依赖，不是源码漂移

排查链（每步都有哈希证据）：

1. 成品收据写「源码 b525ff31」→ 包内源码是 2a14e59f → 先怀疑源码漂移；
2. 校机全盘狩猎 b525ff31（40+ 任务目录、全部 tar.gz 成员、全部散文件）→ 不存在；
3. 行尾假设排除（CRLF/LF 两种规范化哈希都对不上）；
4. r2 任务目录"冻结"tar 包重编 → 得到第三种结果 3c19fc8a → 同源码不同目录出不同二进制；
5. **A/B 定案**：
   - 同一源路径 × 两个不同 build 目录 → 二进制**比特相同**（f0014cd6 = f0014cd6）；
   - 同一内容 × 不同源目录路径 → 二进制**必不同**（10d69f4f）。
6. 结论：**二进制是「源目录绝对路径」的函数**（GCC 默认从源文件路径派生 `-frandom-seed`，局部静态符号名随路径变化）。成品在 `/d/yzd/tmp/wcis-camera-preview-maintenance-3b22a710/ps_app` 编出，换任何路径都得到功能等价、比特不同的二进制。npu_photo 三个程序不含受种子影响的符号，故跨路径比特稳定。
7. 收据里的 b525ff31 后经 `source-map.json` 证实是**源码归档包 tar.gz 的哈希**（`owner_archive_sha256`，同值可查），收据字段名 `source_sha256` 误标——不是丢失的源码版本。已按用户拍板把三份收据字段改名为 `source_archive_sha256` 并同步全部引用清单。
8. 附带澄清：11-03 文档「规范撤回后与保存的 r2 源码逐字节一致」经实测成立，之前怀疑矛盾是因为被收据字段名带偏。

## 过程坑

- **bash --norc 下 PATH 为空**：MSYS2 bash `--noprofile --norc` 不继承 PATH，`dirname` 都找不到。脚本第一行显式 export PATH；任务目录硬编码，不依赖 `$0`。
- **cmd 反斜杠/引号地狱**：ssh 落到 cmd，反斜杠路径传给 MSYS 工具会被吃；复杂管道必须写成 .sh 文件再跑，内联一行式只留 `dir` 这类。
- **上传文件名与脚本内名字对不上**（wcis-src.tgz vs src.tgz）：白跑一轮，远程脚本的输入文件名要和上传清单核对。
- **CMake 4 与 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`**：实测 ps_app 和 npu_photo **不加**该 flag 也能在 CMake 4.4.4 下正常配置（包内 `cmake_minimum_required(3.16)` 与 CMake 4 兼容，CMake 4 只拒绝声明 <3.5 的工程）。该 flag 是 10 月原配方自带的防御参数（遇到声明 <3.5 的第三方 cmake 文件才起作用），保留无害，但别把它当成必需项（初版记录此处有误，已更正）。
- GCC 警告 `parameter passing for argument of type 'std::pair<float,float>' when C++17 is enabled changed to match C++14 in GCC 10.1`（PicPre.hpp:204）——厂商头文件的已知 ABI 提示，十月构建同款，无害。
