# 容器实测记录 — 2026-11-04

本次按用户要求打开独立 Docker 容器，实际执行交付包的 PS 编译流程。没有运行 Vivado/Procise，没有修改板卡。

## 结果

- Windows CPython 3.8.10 调用交付包原有 `find_compiler` 和 `compile_ps`，自动选中本地 `wcis-icraft-test:3.39`；执行包内 `installer/build_ps.sh`。五个目标构建成功，退出码 0；结果均为 AArch64 ELF。
- 编译容器为 Ubuntu 20.04.5，GCC 9.4.0，CMake 3.16.3；SDK 来自本包三个 ARM64 deb 的开发文件，iCraft 3.39.0，OpenCV 4.5.5。另安装 `zlib1g-dev:arm64` 1:1.2.11.dfsg-2ubuntu1.5。
- 编译时 `--network=none`，`source/` 与 `installer/` 只读挂载；构建输出位于独立 `/work`。没有复用之前的对象文件。
- Linux 容器内的 Shell/Python 3.8 两个入口分别校验本包并加载随包 SSH 依赖，十项边界/故障注入测试通过。
- 实际新编译程序已用于生成临时上传包，解包后校验通过，离线生成四项服务；五个 ELF 的哈希与安装树一致，相机服务的哈希参数正确。

## 发现的问题及修正

初次测试仅有 GCC 和 SDK，OpenCV 导出的配置还引用 `/usr/lib/aarch64-linux-gnu/libz.so`，因此链接失败。为独立测试镜像安装 ARM64 zlib 开发库后，重新从空目录构建全部成功。安装器增加对此文件的提前检查，实际缺库镜像被拒绝，不会进入板端安装阶段。不能将“有 iCraft”直接等同于“编译环境完整”。

## 测试环境的来源

Docker Hub 连接失败后，以 Ubuntu 官方基础文件系统建立测试镜像。下载镜像站文件的 SHA-256 已与 [Ubuntu 官方 SHA256SUMS](https://cdimage.ubuntu.com/ubuntu-base/releases/20.04/release/SHA256SUMS) 核对：`60e216b60947653dc8989be3821380268315b99b2959c29882781541bfe5a426`。apt 使用 Ubuntu 镜像源并保留正常签名校验。

`validation/test-image.Dockerfile` 是本次实用配方，仅用于记录测试环境，不是一键入口。若据此重新建立镜像，需要在独立构建目录放置上述 `ubuntu-base.tar.gz`，将本包 `payload/runtime/board/sdk/` 复制为该目录的 `sdk/`，并保证 apt 软件源可访问。根文件系统和整个容器镜像不随本 ZIP 分发；正常安装入口仍使用老师已有的合格 iCraft 镜像。

## 验证边界

这些结果证明编译驱动、源码输入、Linux Python 依赖、上传包生成和离线服务配置可运行。未执行真实板卡更新、重启、SDK 安装、相机/NPU 硬件推理、登记识别、录制回放和长时间稳定性验收。Ubuntu x86_64 编译容器不能代替 FMQL30TAI 板卡。
